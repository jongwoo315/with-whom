# #156 확인 필요에서 사람을 골라 사전에 넣는다 — 설계

## 왜

지금 사람 사전은 연락처 이름만으로 만든다. 그래서 연락처 이름과 다르게 부르는 사람은 매번 「확인 필요」로 간다.
2026-10-29 실측에서 이 티켓 대상이 확인 필요 91개 중 41개였다.

- 연인 호칭 30개: 제목 앞의 호칭이 연락처 이름과 다르다(「호칭 🤍 - 항목」 꼴)
- 연락처에 없는 이름 7개
- 가족 호칭(엄마·아빠) 4개

호칭 하나를 한 번 알려 주면 같은 호칭이 든 일정이 전부 풀린다. 설계 문서 §2의 마지막 줄(「확인 필요에서 jw가 사람을 고르면
사전에 들어가고, 같은 이름은 다음부터 자동으로 잡힌다」)을 만드는 티켓이다.

## 정한 것

| 무엇 | 고른 것 | 이유 |
| --- | --- | --- |
| 무엇을 고르나 | 확인 필요 일정의 제목에서 낱말(토큰) 하나를 고르고, 그 낱말이 가리킬 사람을 정한다. 사람은 이미 있는 사람 중 하나이거나 새 이름이다 | 같은 사람을 다른 호칭으로 부르는 경우(연인 호칭)와 사전에 없는 사람(엄마·지인)을 한 화면에서 처리한다 |
| 사전에 넣는 꼴 | 별칭: 낱말(접미사 뗀 꼴) → 사람 이름. 화면이 접미사 뗀 꼴을 미리 채우고 jw가 고칠 수 있다 | 「성인이」·「성인이랑」이 같은 별칭 하나로 잡히게 한다. 해석 규칙이 이미 접미사를 떼고 찾는다 |
| 별칭 저장 | SwiftData 새 모델 `Alias`(낱말 unique, 사람 이름), App Group 저장 파일 | 가져오기로 다시 만들 수 없는 첫 데이터다. 앱 컨테이너에 있어 iCloud 백업에 들어간다(설계 §4) |
| 별칭과 연락처가 겹칠 때 | 별칭이 우선한다 | jw가 직접 고른 것이 연락처에서 짐작한 것보다 정확하다 |
| 다시 해석 | 별칭을 저장하면 저장된 `Moment` 전부의 제목을 새 사전으로 다시 해석해 사람·항목·확인 필요를 고친다. 캘린더는 다시 읽지 않는다 | 「같은 이름이 든 다른 일정」을 바로 고친다. 사전이 같으면 해석 결과도 같으므로, 이후 가져오기를 다시 눌러도 결과가 되돌아가지 않는다 |
| 가져오기 | 사전을 만들 때 연락처와 별칭을 같이 쓴다 | 새로 들어오는 일정도 별칭으로 잡힌다 |
| 고른 일정 하나만 따로 고치기 | 하지 않는다. 일정별 수동 지정은 저장하지 않고 사전만 바꾼다 | 일정별 지정을 저장하면 가져오기·다시 해석과 충돌을 따로 풀어야 한다. 사전만 바꾸면 결과가 언제나 「제목 + 사전」에서 나온다 |

## 안 고른 것

- `Person`에 별칭 배열을 두기 — 낱말로 바로 찾을 수 없고, 아직 `Person`이 없는 새 이름을 받기 어렵다
- 연락처에서 사람을 고르기 — 연락처에 없는 사람이 7개 + 가족 4개다. 이미 있는 사람 목록과 새 이름 입력으로 충분하다

## 위험

- 띄어쓰기 없이 붙은 제목(「엄마생일」)은 낱말이 통째로 하나라 「엄마」만 고를 수 없다. 이런 일정은 이번 티켓으로 안 풀린다
- 별칭을 지우거나 고치는 화면이 없다. 잘못 넣으면 지금은 되돌릴 수 없다(앱을 지웠다 다시 깔면 저장 파일이 같이 지워진다)
- 「자기가 … 씨 만나는 날」처럼 사람이 잘못 붙는 꼴(#154 견본에서 틀린 1건)은 확인 필요에 오지 않아서 이 화면으로는 못 고친다
